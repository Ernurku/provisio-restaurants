Provisio · Техническое задание · v1 — утверждено

Склад с нормативным учётом остатков + интеграция с Frontpad

Проект: Provisio (back-office доставки) Клиент: доставка роллов, 3 филиала Статус: утверждено, передано в разработку Дата: 26.07.2026

Клиент формулирует боль так: «не проебать остаток продуктов». Ему не нужна классическая инвентаризация — нужно, чтобы система сама считала, сколько сырья должно было остаться после продаж, и подсвечивала расхождение с тем, что намерил повар. Это новый функционал поверх существующего Provisio, не мелкая правка.

01Границы задачи

Три корзины — что делаем сейчас, что остаётся отложенным, и что не входит в Provisio никогда (это решено в разговоре с владельцем продукта, не подлежит обсуждению с клиентом-рестораном).

Phase 1 — сейчас

  • Дашборд, Меню, Рецепты, Калькулятор, Закупки, Ингредиенты, Поставщики, Настройки (без изменений)
  • Склад — восстановить + переработать под норматив/факт
  • Интеграция с Frontpad — источник данных о проданных блюдах

Phase 2 — без изменений

  • Заказы поставщикам (Orders)
  • Команда / приглашения
  • Уведомления
  • Приложения / интеграции

Не входит в Provisio никогда

  • CRM / рассылки в WhatsApp
  • Авто-дожим брошенных заказов
  • Разбивка выручки Kaspi vs нал (налоговая оптимизация клиента)
Почему WhatsApp-автоматизация исключена

Официальный WhatsApp Business Cloud API требует одобренные Meta шаблоны для любых исходящих сообщений вне 24-часового окна диалога — «дожим» брошенной корзины в них не проходит гладко. Неофициальные библиотеки (Baileys, whatsapp-web.js), которыми пользуется большинство малого бизнеса, прямо нарушают ToS WhatsApp — систематическая проактивная рассылка без явного opt-in — это ровно тот паттерн, на который реагирует антиспам Meta, вплоть до блокировки номера. Это отдельный проект с отдельными рисками, не часть Provisio.

03Модуль «Склад»: восстановить ≠ то, что нужно

Проверил архивный admin-inventory.js и таблицу inventory в supabase_schema_new.sql — это простой статичный склад (добавил количество вручную → алерты по min_stock и сроку годности). Он не связан с продажами и не считает норматив. Разворачивать его «как есть» не решает боль клиента — это лишь часть фундамента.

СлойИсточникЧто делать
A — базовый UI складаЕсть в архивеВосстановить категории, таблицу, алерты low-stock/expiry. Попутно починить баг: JS использует min_stock_level/minStock, схема — min_stock (та же болезнь, что в ДИАГНОСТИКА.md).
B — норматив/факт (ядро фичи)Нет нигдеНовая логика: expected_quantity = предыдущий остаток − Σ(продано блюд × расход по рецепту с EP%), сверх существующего ReactiveEngine. Плюс поля actual_quantity, last_recount_at, variance.
C — экран «Быстрый контроль»Нет4 колонки: Ингредиент → Расчётный остаток → Факт от повара → Расхождение (красным при недостаче сверх порога, напр. 5%).

04Модуль «Frontpad»: реальные находки, не предположения

Разведал публично доступную документацию (Frontpad не публикует официальный developer-портал — сведения собраны из документации сторонних интеграторов: DLVRY, FoodSoul, Chibbis).

МетодНаправлениеЧто делает
new_order→ в FrontpadОтправить заказ из внешнего источника в Frontpad
get_products← из FrontpadКаталог товаров: массивы id / название / цена
get_status← из FrontpadСтатус заказа по id или телефону
get_client← из FrontpadДанные клиента по телефону
get_certificate← из FrontpadПроверка сертификата/бонуса
webhook← из Frontpad, pushУведомление об изменении статуса заказа (URL + secret настраиваются в Frontpad → Настройки → Общие → API)
Открытый технический риск — нужен спайк перед оценкой сроков

Публичный API Frontpad явно заточен под отправку заказов в Frontpad (интернет-магазин → касса), а не под выгрузку истории продаж наружу. Задокументированного метода «отдай мне все проданные позиции за день» нет. Webhook у сторонних интеграторов используется в первую очередь для синхронизации статусов — не гарантировано, что он присылает полную построчную корзину (какое блюдо, сколько штук) на каждый завершённый заказ.

Прежде чем проектировать модуль B (норматив), нужен разведывательный шаг с реальным API-секретом клиента: сделать тестовый заказ, посмотреть фактический payload вебхука, проверить get_products на реальном каталоге. Если построчной корзины в вебхуке нет — придётся либо запрашивать у поддержки Frontpad отдельный отчётный доступ, либо на первое время принимать ежедневный экспорт (CSV) из панели Frontpad как временный источник, пока API-доступ не подтверждён.

Дополнительно: товары Frontpad (product_id) нужно сопоставить с рецептами Provisio — сейчас в схеме нет такого поля. Понадобится, например, recipes.frontpad_product_id и экран ручного маппинга на случай, если названия/id не совпадают 1:1.

05Дисциплина именования полей

В проекте уже есть системная проблема — компонент сохраняет данные под одним именем колонки, а читает под другим (см. ДИАГНОСТИКА.md: calculated_cost vs cost, sale_price vs price, и т.д.). Всё новое в этом модуле обязано сверяться с канонiческими именами v8 схемы до реализации, а не после первого бага.

06Критерии готовности

  • Вкладка «Склад» открывается, показывает реальные данные, low-stock/expiry алерты работают, баг с именем поля min_stock устранён
  • Тестовый заказ во Frontpad отражается в Provisio как расход ингредиентов в течение согласованного окна (напр. 15 минут)
  • Повар может ввести фактический остаток с телефона; расхождение выше порога подсвечивается
  • Ни один экран Provisio не отправляет и не показывает данные WhatsApp/CRM/способов оплаты
  • Прогон полного цикла: продажа → списание → сверка — на реальных данных клиента перед презентацией

07Вопросы к клиенту на встрече

  • Кто вечером вводит фактический остаток — старший повар с телефона или сам владелец раз в день?
  • Можно ли получить тестовый API-секрет Frontpad заранее, чтобы разведать реальный формат вебхука до встречи?
  • Совпадают ли названия блюд в Frontpad с рецептами в Provisio 1:1, или там разные наименования / позиции-модификаторы (соусы, добавки), которые тоже расходуют сырьё?
